# Project Audit Logging

In this project, I enabled audit logging on the API servers of my homelab cluster. Before the change, the cluster kept no record of who did what. A user could read every Secret in a Namespace, and nothing showed it afterward. After the change, every API server writes each request to a log file: who sent it, what they did, and whether the API server allowed it.

An audit log answers the questions after an incident. Which user read the Secret? When did someone create that RoleBinding? Who ran a shell in that Pod? Without logs, you can't investigate an attack or prove that nothing happened.

---

## The Plan

The cluster has three control plane nodes, each with its own API server. HAProxy sends each request to one of them. Every API server needs the same audit policy, and each one writes only the requests it handled.

I create one policy file, copy it to the three control plane nodes, and change the API servers one at a time. Then I use the `hans-dev` user from [RBAC Users](/articles/kubernetes/cks/2-rbac-users/) to read Secrets and find the requests in the logs.

The project uses these names and values:

| Item              | Value                                                                     |
| ----------------- | ------------------------------------------------------------------------- |
| Policy file       | `/etc/kubernetes/audit/audit-policy.yaml` on every control plane node     |
| Log file          | `/var/log/kubernetes/audit/audit.log` on every control plane node         |
| Manifest backup   | `/etc/kubernetes/backups/` on every control plane node                    |
| Test user         | `hans-dev`, with the `edit` ClusterRole in the Namespace `dev`            |
| Test Secret       | `db-secret` in the Namespace `dev`                                        |

## How Auditing Works

The API server creates an audit event for every request. The policy decides how much of each event it writes.

### Audit Levels

Each rule in the policy sets one of four levels:

| Level             | What the API server writes                                          |
| ----------------- | ------------------------------------------------------------------- |
| `None`            | Nothing                                                             |
| `Metadata`        | The user, the time, the resource, the verb, and the response code   |
| `Request`         | The metadata and the request body                                   |
| `RequestResponse` | The metadata, the request body, and the response body               |

The first rule that matches a request sets its level. Put the specific rules at the top and the catch-all rule at the bottom.

> **_Warning:_** At the `Request` or `RequestResponse` level, the audit log contains the Secret values. Log Secrets at the `Metadata` level only.

### Stages

An event can be written at several stages of a request:

- `RequestReceived`: The API server received the request.
- `ResponseStarted`: The response headers are sent. Only for long-running requests, such as `watch`.
- `ResponseComplete`: The response is complete.
- `Panic`: The API server panicked while handling the request.

> **_Note:_** Most policies skip `RequestReceived`. It doubles the number of events without adding the response code.

## Step 1: Write the Audit Policy

The policy records security-relevant events while excluding routine requests generated by the cluster every second.

```yaml
apiVersion: audit.k8s.io/v1
kind: Policy
omitStages:
  - RequestReceived
rules:
  - level: None
    nonResourceURLs:
      - /healthz*
      - /livez*
      - /readyz*
      - /version
  - level: None
    resources:
      - group: coordination.k8s.io
        resources: ["leases"]
  - level: None
    resources:
      - group: ""
        resources: ["events"]
  - level: Metadata
    resources:
      - group: ""
        resources: ["secrets", "configmaps"]
  - level: RequestResponse
    verbs: ["create", "update", "patch", "delete"]
    resources:
      - group: rbac.authorization.k8s.io
        resources: ["roles", "rolebindings", "clusterroles", "clusterrolebindings"]
  - level: Metadata
```
- `omitStages`: Skips the `RequestReceived` stage for all rules.
- `nonResourceURLs`: The health checks that run every few seconds and show nothing about users.
- `leases` and `events`: The controllers and kubelets update them constantly.
- `secrets` and `configmaps`: Logged at `Metadata`, without the values.
- `rbac.authorization.k8s.io`: Changes to permissions, with the full request and response.
- `level: Metadata`: Logs every other request at `Metadata`.

Save the file as `audit-policy.yaml` on the laptop.

## Step 2: Copy the Policy to the Control Plane Nodes

All three API servers need the same policy. With different policies, one node's log shows events that another node doesn't have.

**Copy the file to every control plane node**
```bash
for node in master-1 master-2 master-3; do
  scp audit-policy.yaml $node@k8s-$node:/tmp/
  ssh -t $node@k8s-$node "sudo mkdir -p /etc/kubernetes/audit && \
    sudo mv /tmp/audit-policy.yaml /etc/kubernetes/audit/ && \
    sudo chown root:root /etc/kubernetes/audit/audit-policy.yaml"
done
```

## Step 3: Configure the API Servers

The kubelet restarts the `kube-apiserver` Pod when its manifest changes. I change one node at a time and wait until its API server is back. The other two API servers keep the cluster available behind HAProxy.

### Back Up the Manifest

A mistake in the manifest stops the API server on that node. A backup lets me roll back fast.

**Create the backup directory on the `k8s-master-1` node**
```bash
sudo mkdir -p /etc/kubernetes/backups
```

**Copy the kube-apiserver manifest**
```bash
sudo cp /etc/kubernetes/manifests/kube-apiserver.yaml \
  /etc/kubernetes/backups/kube-apiserver.yaml.$(date +%Y-%m-%d)-audit-backup
```

### Edit the Manifest

The API server needs the flags, read access to the policy, and write access to the log directory. Open `/etc/kubernetes/manifests/kube-apiserver.yaml` and add the required flags and volumes.

Add the flags to the `command` of the container:
```yaml
- --audit-policy-file=/etc/kubernetes/audit/audit-policy.yaml
- --audit-log-path=/var/log/kubernetes/audit/audit.log
- --audit-log-maxage=30
- --audit-log-maxbackup=10
- --audit-log-maxsize=100
```
- `--audit-policy-file`: The location of the policy.
- `--audit-log-path`: The location of the log file.
- `--audit-log-maxage`: The number of days to keep old log files.
- `--audit-log-maxbackup`: The number of rotated log files to keep.
- `--audit-log-maxsize`: The size in megabytes at which the log file rotates.

These are the same settings as the CIS Kubernetes Benchmark recommendations.

Add the `volumeMounts` to the container:
```yaml
volumeMounts:
  - name: audit-policy
    mountPath: /etc/kubernetes/audit
    readOnly: true
  - name: audit-log
    mountPath: /var/log/kubernetes/audit
    readOnly: false
```
- `audit-policy`: Read-only. The API server only reads the policy.
- `audit-log`: Writable. The log goes to the node and survives a restart of the Pod.

Add the `volumes` to the Pod spec:
```yaml
volumes:
  - name: audit-policy
    hostPath:
      path: /etc/kubernetes/audit
      type: DirectoryOrCreate
  - name: audit-log
    hostPath:
      path: /var/log/kubernetes/audit
      type: DirectoryOrCreate
```

> **_Warning:_** The audit log shows the names of all Secrets, users, and requests. Only the control plane nodes should read it.

## Step 4: Generate Events

The test requests come from the laptop, with the kubeconfig of `hans-dev`. This user has the `edit` ClusterRole in `dev` only.

**Create a test Secret as admin**
```bash
kubectl --kubeconfig ~/.kube/rbac-users/hans-adm.conf -n dev create secret generic db-secret --from-literal=DB_PASS=super
```

**Read the Secret as `hans-dev`**
```bash
kubectl --kubeconfig ~/.kube/rbac-users/hans-dev.conf -n dev get secret db-secret -o yaml
```
```

  DB_PASS: c3VwZXI=
```

The request is allowed. The `edit` ClusterRole can read Secrets in `dev`.

**Try to list the Secrets in `kube-system` as `hans-dev`**

The request is forbidden. The audit log records the attempt too.

**Create a Pod as `hans-dev`**

## Step 5: Find the Events

Each API server only logs the requests it handled. HAProxy spreads the requests over the three nodes. Search the log on every node.

**Show the Secret requests of `hans-dev` on every control plane node**
```bash
for node in master-1 master-2 master-3; do
  echo "== $node"
  ssh -t $node@k8s-$node "sudo jq -c 'select(.user.username==\"hans-dev\" and .objectRef.resource==\"secrets\") | {time: .stageTimestamp, verb, ns: .objectRef.namespace, name: .objectRef.name, code: .responseStatus.code, decision: .annotations[\"authorization.k8s.io/decision\"]}' /var/log/kubernetes/audit/audit.log"
done
```
- `.user.username`: The user who sent the request.
- `.objectRef`: The resource, Namespace, and name of the object.
- `.responseStatus.code`: `200` for an allowed request, `403` for a forbidden one.
- `authorization.k8s.io/decision`: `allow` or `forbid`.
```

Connection to k8s-master-1 closed.
```

## Step 6: Persist During Cluster Upgrades

The flags and volumes live in the `kube-apiserver` manifest. When kubeadm upgrades the nodes, it regenerates the manifest from the `ClusterConfiguration` in the `kubeadm-config` ConfigMap, and removes what you added by hand.

**Back up the ConfigMap on the first control plane node**
```bash
kubectl -n kube-system get cm kubeadm-config -o yaml | \
  sudo tee /etc/kubernetes/backups/kubeadm-config.yaml.$(date +%Y-%m-%d)-audit-backup
```

**Edit the ConfigMap**
```bash
kubectl -n kube-system edit cm kubeadm-config
```

Add the flags and volumes under `apiServer`, next to the fields that are already there:

```yaml
apiVersion: kubeadm.k8s.io/v1beta4
kind: ClusterConfiguration
apiServer:
  extraArgs:
  #...
  # K8S Audit
  - name: audit-policy-file
    value: /etc/kubernetes/audit/audit-policy.yaml
  - name: audit-log-path
    value: /var/log/kubernetes/audit/audit.log
  - name: audit-log-maxage
    value: "30"
  - name: audit-log-maxbackup
    value: "10"
  - name: audit-log-maxsize
    value: "100"
  extraVolumes:
  #...
  # K8S Audit
  - name: audit-policy
    hostPath: /etc/kubernetes/audit
    mountPath: /etc/kubernetes/audit
    readOnly: true
    pathType: DirectoryOrCreate
  - name: audit-log
    hostPath: /var/log/kubernetes/audit
    mountPath: /var/log/kubernetes/audit
    readOnly: false
    pathType: DirectoryOrCreate
#...
```
- `value`: Always a string. Put numbers in double quotes.
- `extraVolumes`: Becomes both the `volumes` and the `volumeMounts` entries in the manifest.

## Common Errors

| Error                                                    | Cause                                                                | Fix                                                                       |
| -------------------------------------------------------- | -------------------------------------------------------------------- | ------------------------------------------------------------------------- |
| The `kube-apiserver` Pod doesn't come back               | A wrong path, a missing volume, or a YAML error in the policy        | Read the logs in `/var/log/pods/kube-system_kube-apiserver-*/`            |
| The log file stays empty                                 | `--audit-log-path` is missing, or the log volume isn't mounted       | Check the flags and the `audit-log` volume                                |
| The log shows the Secret values                          | Secrets match a rule with `Request` or `RequestResponse`             | Put the `Metadata` rule for Secrets above the other rules                 |
| An event is missing on one node                          | HAProxy sent the request to another API server                       | Search the logs on all three control plane nodes                          |
| The log fills the disk                                   | No rotation, or the policy logs too much at a high level             | Set `--audit-log-maxsize` and `--audit-log-maxbackup`, and skip the noise |

## Conclusion

Audit logging is enabled, and the API server logs every request with a user, a time, and a result. With RBAC from the earlier project, each person has their own user. The log shows who did what, not only that `kubernetes-admin` did something.

The log only covers requests to the API server. A process that runs inside a container, or a user who logs in to a node with SSH, never reaches the API server. Falco, the next project, watches the system calls on the nodes and covers that gap.

For production, send the logs to a central system, such as Loki or Elasticsearch. A log on the control plane node is lost with the node, and an attacker with root on the node can change it.

## Reference

| Concept                    | What it means                                                         |
| -------------------------- | --------------------------------------------------------------------- |
| Audit policy               | The rules that decide what the API server logs, at which level        |
| `None`                     | Doesn't log the request                                               |
| `Metadata`                 | Logs the user, the verb, the resource, and the response code          |
| `Request`                  | Also logs the request body                                            |
| `RequestResponse`          | Also logs the response body                                           |
| `omitStages`               | The stages to skip, usually `RequestReceived`                         |

## Best Practices

- Log Secrets and ConfigMaps at the `Metadata` level only.
- Log changes to RBAC at the `RequestResponse` level.
- Skip health checks, leases, and events to keep the log small.
- Put the specific rules first and the catch-all rule last.
- Use the same policy on every control plane node.
- Rotate the log with `--audit-log-maxsize`, `--audit-log-maxbackup`, and `--audit-log-maxage`.
- Send the logs to a central system that the control plane nodes can't change.

---

## CKS Exam Takeaways

- Audit logging needs two flags: `--audit-policy-file` and `--audit-log-path`.
- Mount the policy read-only and the log directory writable with `hostPath` volumes.
- The first matching rule sets the level. Order matters.
- `kind: Policy` with `apiVersion: audit.k8s.io/v1`, and at least one rule.
- Search the log with `jq`, for example on `.user.username`, `.objectRef.resource`, and `.verb`.
- A broken policy stops the API server. Check `/var/log/pods/` when it doesn't come back.
